# DFX 12 维度测试策略矩阵

本文件用于约束异常值、边界值、性能、安全、兼容、可靠性等测试策略的生成方式，避免只写一句笼统策略。每个批次、每个小功能块、每个可交互页面元素都应基于适用的 DFX 维度选择具体场景，并落到正式测试设计的测试点、测试数据、操作步骤和预期结果中。

## 生成规则

- 模块或批次正式写测试用例前，必须先做 DFX 覆盖评估：结合产品理解摘要、页面实探、需求/设计/接口文档、历史归档、测试数据和风险项，逐项判断 12 个维度及 4 类场景是否适用于当前模块。
- DFX 覆盖评估的准入条件是当前批次深探已经通过准出门禁：基线元素和动态新增元素均有处理结果，主要流程形成安全闭环，页面可验证风险与用户补充产生的新目标已完成定向补探，最终收口复查不再产生新元素，且实探结果/用户说明/设计预期已区分。页面可访问且仍存在可操作的 `待实探` 项时，不得进入 DFX 或用例生成。
- 深探、文档、历史资产和用户说明中的事实必须先按测试对象、角色/状态、动作/输入、数据、观察点和恢复路径形成并核账原子场景，再标记主 DFX。DFX 可以补充新的质量场景，不得用维度归类、代表性抽样或去重删减已经形成的不同功能事实。
- 需要接口、日志、权限、环境、关联数据或联调支持的事项，以及明确不测、延期或不适用项，可以带着原因进入 DFX，并落到风险或性能设计中；不得为满足准入条件伪造页面证据。
- DFX 覆盖评估必须输出适用、不适用、待确认和需补充证据的结论；适用项进入功能测试用例或性能测试设计，不适用项说明原因，自动化适合度按需写入功能测试用例。`待确认` 只用于新发现的业务理解问题，必须展示编号清单并结束当前轮次；收到用户后续明确回复前不得进入用例生成。接口、日志、环境、权限或联调不足属于需补充证据，不作为用户理解确认问题。
- DFX 覆盖评估不能只停留在 `dfx-assessment.md` 或过程说明中；正式测试设计必须在 `测试场景矩阵`、`功能测试用例`、`性能测试设计`、`风险与待确认问题` 和 `页面元素覆盖清单` 中填写对应的 `DFX维度` 与 `DFX场景` 字段。
- `场景类型`、`正向/反向` 已废弃，不能继续作为测试策略字段；正向、反向、异常、边界等策略统一通过 `DFX场景` 表达。
- 不得只写“异常值、边界值、性能测试需覆盖”等一句话；必须说明适用维度、具体场景、触发数据、操作路径、观察点、预期结果和恢复路径。
- 每个小功能块默认至少覆盖 DFT 功能、DFB 业务、DFS 安全或权限、DFR 可靠或数据一致、DFU 可用性；有接口、性能、部署、运维、兼容特征时追加对应维度。
- 页面元素类用例必须把 DFT 的正向流程、边界值、异常输入、逆向操作转化为可执行步骤，例如输入最大长度、空值、重复值、非法格式、取消/关闭/返回、重复提交和数据不变。
- 性能相关场景必须写入 `性能测试设计` Sheet，不得只放在功能测试用例备注中；性能场景应明确目标用户量/并发数、响应时间目标、数据量级、监控指标、通过标准和造数策略。
- 接口、超时、重试、幂等、数据一致、日志、告警、监控、回滚等系统性场景如果当前页面无法直接执行，应写入风险与待确认问题或性能测试设计，并说明需要的接口、日志、监控或环境支持。
- 破坏性、资源耗尽、并发极限等 DFX 极端场景不得在共享或生产样数据上直接执行；仅允许在隔离测试环境、压测环境或本次创建的测试数据上设计，并明确安全边界、回滚或清理策略。

## 从功能点展开测试场景

- 当前项目采用轻量父子结构：`功能点` 作为父场景和用例分组，不新增父场景 ID、测试对象 ID、落地类型或落地 ID 等 Excel 字段。
- 每个功能点先识别业务流程、操作步骤、页面元素、接口和数据对象，再从适用的 DFX 维度展开原子测试点。一个业务场景可以包含多个对象，也可以涉及多个 DFX 维度，但必须拆成可追踪的原子场景行。
- `测试场景矩阵` 每行只填写一个主 `DFX维度` 和一个对应的 `DFX场景`。DFX 不能只改变标签，必须实际改变角色、状态、数据、动作、环境、观察点或恢复路径中的至少一项。
- `场景 ID` 在工作簿内唯一；建议使用同一功能点前缀连续编号，例如 `SCN-USER-CREATE-01`、`SCN-USER-CREATE-02`，但校验器不强制命名正则。
- `测试对象/页面元素` 使用现有字段记录本行直接验证的页面元素、接口、数据对象或业务链路。多个元素共同完成同一测试目标、共享前置条件和操作链路时，可以合并为一个链路场景；观察目标、状态条件或恢复路径不同时应拆分。
- 场景去重以 `Story ID/需求 ID + 功能点 + 测试对象/页面元素 + DFX维度 + DFX场景 + 输入数据/状态条件 + 观察点` 为精确签名。完全相同的场景必须合并；仅 DFX 标签相同而数据、状态或观察点不同的场景不是重复。
- 不得机械执行“元素 × 12 维度 × 4 场景”的笛卡尔积。先判断适用性，再生成能够改变测试输入或验证目标的场景。

## 用例落地格式

生成功能测试用例时，每条用例必须填写 `DFX维度` 和 `DFX场景`，并在 `测试数据`、`操作步骤`、`预期结果` 至少体现：

1. 维度与场景：例如 `DFT-边界值`、`DFS-权限控制`、`DFR-幂等性`。
2. 输入或状态：正常值、边界值、非法值、重复值、无权限角色、异常状态、超时/重试条件、并发条件等。
3. 观察点：页面提示、字段校验位置、按钮禁用态、数据落库、列表刷新、状态流转、日志/审计、通知、接口错误码、监控指标。
4. 预期结果：成功、失败、拦截、数据不变、可恢复、可重试、回滚成功、告警触发或指标达标。

场景矩阵保持原子化，但一个最终用例可以落地多个相容场景：仅当前置条件、测试数据和操作步骤相同，且各 DFX 观察点与预期结果均能清晰对应时才允许合并。若角色、数据、状态、动作或恢复路径任一不同，必须拆为独立用例。每条用例都必须形成可独立执行的小业务闭环，包括入口与导航、前置状态或造数、关键动作、结果/数据/状态验证，以及取消、恢复、回滚或清理路径；不能只验证孤立控件动作。

## 批次自检

每批完成前，应检查：

- 功能测试用例是否至少覆盖当前小功能块适用的 DFT、DFB、DFS、DFR、DFU 场景。
- 性能测试设计是否覆盖 DFP 响应时间、并发处理、大数据量和资源监控中适用场景。
- 风险与待确认问题是否记录当前无法验证但对产品质量重要的 DFI、DFD、DFO、DFX 场景。
- 页面元素覆盖清单中的输入、选择、按钮、弹窗、表格行操作、批量操作、分页、筛选、排序等元素是否都映射到可执行 DFX 场景或明确标注不适用原因。
- 同一功能点是否仍有只改变 DFX 标签、没有改变输入/状态/观察点的同质场景；相同步骤用例是否可以在不损失 DFX 对应关系和业务闭环的前提下合并。
